# Case structure

## Full format (single case or chosen case)
Number them: "Case 1 – [name]".

| Section | Content |
|---|---|
| **Presenter and Area** | Who presented the case and from which area. If not mentioned: [not provided]. |
| **Case presented** | The process or situation reported, as it happens today. |
| **Pain** | The main bottleneck or pain of the current process. |
| **Goal** | What the solution must achieve. |
| **What it solves** | The direct effect of the solution on the pain. |
| **Impact** | Who and how much the case affects: area, volume, frequency, time or risk, as reported. |
| **Value** | Concrete, specific benefit of the build, without generalizations. |
| **Classification** | Adherent or Viable as a project (complexidade.md). |
| **Build complexity** | Low, Medium or High, with justification. Adherent cases only. |
| **Sustainment complexity** | Low, Medium or High, with justification and what the client will need to maintain. Adherent cases only. |

## Summary format (selection report)
Used when the meeting brings several cases. One block per case, in this order: adherent cases first, then those viable as a project.

| Field | Content |
|---|---|
| **Case** | Number and name. |
| **Pain** | One or two sentences. |
| **What it solves** | One or two sentences. |
| **Impact** | One sentence. |
| **Value** | One sentence. |
| **Classification** | Adherent (build X, sustainment Y) or Viable as a project. |

At the end of the report, a summary: total cases, how many adherent and how many viable as a project.

## Filling rules
- Each case is an independent unit, even if it comes up in the same interview or area as another.
- Write based on what was reported; do not invent systems, integrations, participants or numbers.
- Field without information: [not provided].
- Do not mention the solution type (prompt, agent, project) in the case text.
